Work OS 101

For Everyone · Time 8 min read

Your platform

The Work OS is a shared operating system for product work with Claude: a governed repository of context (what the team knows), skills (how the team works) and rules (what may change, and how) that Claude reads, uses and keeps up to date. It turns Claude from a chat window into a team asset — one that compounds as people use it.

Three terms: LLM, agent, agent OS

What it isOne line
LLM — answersA model that answers one prompt at a time: it reads what you give it and writes back. No memory, no tools, no initiative.Claude Chat, ChatGPT
Agent — actsAn LLM in a loop with tools: it plans, takes multi-step actions (reads files, searches, writes), checks results and iterates until the job is done.Claude Code
Agent OS — compoundsAn agent working inside a dynamic, maintained operating system: a governed repository of skills and a context system it reads, uses and keeps up to date.Claude Code + the Work OS repository — this is the Work OS

Why a shared OS beats a private chat

Product work runs on context — who the customer is, what was decided, what the numbers say, what the team agreed a good PRD looks like. Without a Work OS, that context lives in people's heads and private chats, so every AI answer starts from zero and every PM re-teaches their own assistant. The Work OS puts that context in one shared, versioned place and gives every teammate's Claude the same skills, so:

  • Answers are grounded — Claude reads your business context, strategy and decisions before it drafts, and cites them.
  • Best practice is shared — the team's way of writing a PRD, running a meeting or sizing a feature is one skill everyone runs, and improving it once improves everyone's next result.
  • The system learns — corrections become rules; what one person fixes, nobody has to fix again.
  • It stays safe — access rules, a write policy and review flows keep a shared system auditable and trusted.

The underlying technology

Nothing exotic — three well-understood parts, each replaceable:

  • Claude Code — Anthropic's agent. It runs on your computer (the desktop app), reads and writes files in the Work OS folder, runs skills, and talks to your tools through MCP connectors.
  • A git repository — plain Markdown and YAML files in folders, versioned in GitHubAzure Repos. Git is how developers have shared and versioned work for years; here it carries the team's knowledge instead of code — audited, updated and versioned by default, tool-agnostic.
  • Auto-sync and the write policy — a small set of scripts and one policy file inside the repository. They save your work automatically, move everyday changes to the shared branch, and route changes to gated files through an approval. See Team collaboration.

Where it lives — the repository

Everything is a file in one folder tree. The same tree is on every teammate's computer and in GitHubAzure Repos; the Context system article walks through it item by item.

One loop keeps every copy of this tree identical — yours, your teammates' and the shared one — without anyone running git commands. Team collaboration shows how.

Context system

For Everyone · Time 7 min read

The context system is everything Claude knows before you ask — the files of the Work OS repository. Skills read it before they write a word, answers cite it, and every call, decision and research finding lands back into it. This article is the tour: the six kinds of files, the map of what lives where, and how material flows in and answers flow out.

Six kinds of files

Every file in the Work OS is one of six kinds, and the kind tells you how to treat it: who writes it, how it changes, how much to trust it. The colored labels below mark every item in the map that follows.

Steering file

Loaded first or automatically; shapes how Claude behaves everywhere.

Maintained by people, changed deliberately — most are gated behind the 🔒 prompt and an admin's approval.

Registry

A machine-readable lookup (YAML) that maps names to artifacts.

Updated by skills as they file their work; rarely edited by hand.

Living page

The current truth on one subject, edited in place.

Read first for "what's the state of …" — skills keep it current.

Raw material

Evidence as it arrived — transcripts, records, monitoring runs.

Appended, never rewritten; the grounding underneath every summary.

Deliverable

Skill outputs — PRDs, job specs, reports, syntheses.

Written by skills; iterate through the skill that owns the file.

Template & guide

The reference a skill follows — blank scaffolds and writing guides.

Copied, never edited in place; templates are gated.

How material gets in

Everything the team learns arrives as something: a call recording, a deck, a thread, a customer's email. Material that stays in your inbox is material Claude cannot use.

What you haveWhat to use
A call, interview or internal meeting — transcript, notes or dictation/process-meeting. Drop the file into product-development/inbox/, or point Claude at it. It files the transcript, writes the summary where that kind of meeting belongs, and routes the decisions and feature requests out of it.
A document, deck or pasted thread that is not a meeting/context-update — folds the content into the pages it belongs to and links them up.
A decision taken somewhere else/decision-log-entry — a dated record with the reasoning, the options and the tradeoff accepted, so the debate is not reopened next quarter.

Sensitive material is handled by rule, not by memory: summaries name customer-side people by role only (the raw transcript underneath stays a faithful record), salary and revenue figures belong in your CRM rather than in the summaries, and health details are kept out of the summary and the filed transcript alike. The Privacy Contract in CLAUDE.md lists what may never be committed at all — 1:1 and coaching notes, performance feedback, comp and board material, credentials. Skills and agents

For Everyone · Time 8 min read

A skill is a named, reusable workflow: you type /skill-name (or just ask in plain words) and the team's agreed way of doing that piece of work runs — reading the right context first, writing the result to the right place. An agent is a specialist Claude spins up for part of a job: a reviewer with a fixed perspective, or a read-only code explorer. Skills live in .claude/skills/, agents in .claude/agents/; both are versioned with the repository, so improving one improves it for everyone.

From idea to handoff — where each skill runs

One feature travels four stages — idea, discovery, definition, handoff — and each skill reads what the one before it wrote: the evidence gathered in discovery is the evidence the job spec cites, so nothing is re-typed and nothing is re-decided.

Idea

One page states the bet: the problem, who has it, why now. The first draft marks what it does not know instead of inventing it.

/prd-draft

The gaps that need evidence get filled. Talking to customers stays human work — Claude prepares the interview, then works up what comes back.

The bet is challenged from every side, cut into independently shippable jobs, and each job gets a contract precise enough to build from.

/jobs-breakdown/job-spec-draft/prd-challenge/job-spec-challenge/prototype

Note

The stages are not four weeks in a plan. Discovery and definition interleave: you challenge a draft, find a hole, run one piece of research, and update the same PRD.

How the PRD stays current

/prd-draft is not a one-time write. Run it again whenever the initiative moves and it re-reads the evidence attached to that initiative, updates the draft, and leaves three things behind:

  • [GAP:] markers where a section is not backed by anything — the draft says so rather than filling the hole with a plausible number.
  • Closed gaps, for the ones Claude can close by itself: up to three pieces of research per run, and only where the source actually exists.
  • A readiness readout — what moved, what is backed, what is still an assumption, who owns each open gap, and every file it touched.
Why this matters

A gap you can see is worth more than a sentence that reads well. [GAP:] markers are what the handoff gate counts at the end, so an unclosed gap blocks the handoff instead of reaching the BA unnoticed.

What one skill run looks like

Every skill in the chain behaves the same way, whichever one you call:

  1. It reads first — business context, this quarter, the initiative page, the research and competitive material — before it writes a word.

  2. You ask in one sentence. "Draft the PRD for expense management." The skill name and plain words both work.

  3. It asks only what is missing. The first run on a new document stops once, to agree the open essentials and what it is about to write; one yes covers the rest of the run.

  4. It writes to the agreed place — the deliverable, the initiative page and the feature index — not a chat answer you have to file yourself.

  5. It ends with a readout: what it did, what is still open, and the decisions only you can make.

Tip

You can ask what a skill will read before you run it — worth doing when you suspect the context is thin.

The two challenge passes

/prd-challenge and /job-spec-challenge are the passes that stop a comfortable draft from going forward. Both run every critique lens at once and blind to each other, then merge everything into one report — and the lenses fit the document. The PRD pass sends in the reviewer agents, an assumption map, a red team and — once there is a solution and a rollout to test — a rehearsal of the failed launch; its report leads with the assumptions nobody has verified and the next research step for each. The job-spec pass reads the contract the way the people who will build from it read it — the rules and acceptance criteria, testability, feasibility — and its report leads with one verdict: ready to become tickets, or not.

  • Neither pass edits the document. The rewrite happens on your yes, through the skill that owns the file.
  • Neither runs by itself — you ask for a challenge when the draft is worth challenging.
  • Where reviewers contradict each other, the contradiction is kept visible rather than averaged away. It is usually the interesting part.

The handoff gate

/pm-handoff is the check before requirements leave you for the BA, technical PM or product owner. Four checks across the whole package — the PRD, the breakdown and every job spec — each finding cited to the file and line it came from:

  • No open [GAP:], TBD or unvalidated items left, and no unchecked engineering confirmations.
  • Prototype links present and resolving — or a stated reason there are none.
  • Approval recorded in the documents' own status fields. A verbal yes does not count.
  • No template section quietly missing.

The verdict is READY or NOT READY, with a fix route for each failure. After a READY, /create-tickets cuts the dev backlog from the same documents.

How an everyday change lands

  1. You ask Claude for something — a meeting summary, a decision record, a customer note. Claude writes the file.

  2. When Claude finishes the response, auto-sync saves the change to your personal branch in the shared repository (a branch is a private working line; yours is named sync/<your git name>).

  3. Auto-sync opens a small pull request from that branch into main — the team's shared line — and it merges by itself. Nobody has to look at it.

Check in GitHubAzure Repos

On the repository page you'll see the file on main within about a minute, and under Pull requests › ClosedCompleted a pull request called "context: sync from sync/<name>".

How a gated change lands

  1. You ask Claude to change a gated file. Before writing, Claude shows a 🔒 GATED FILE prompt — you read the change and approve it.

  2. When Claude finishes, auto-sync saves the change to your personal branch — but not to main. It waits there while you keep iterating.

  3. When you're done, you say "propose the gated changes". Claude opens a pull request with a plain-language description of everything that changed.

  4. A Work OS admin reviews it — in GitHubAzure Repos, by asking their own Claude, or on the Proposed changes page of the Work OS console, where one click approves and mergescompletes it, and a rejection posts the admin's comment on the pull request. GitHubAzure Repos won't let anyone else. (An admin publishing their own gated change can ask Claude to do all three at once — see Customize the Work OS, step 3.)

  5. Next time Claude finishes a response, your branch tidies itself — the approved change is now part of main for everyone.

Two parts, in this order: first the Work OS admin connects a tool once and lets Claude record which skills use it — that record is shared with the team. There are two ways to make a connection, and the walkthroughs below are written for both. Connect your product's codebase

For Stage 2 · Work OS admin, with the admin of your code repositories — then each user on their own computer · Time about 30 minutes, plus 15 per extra repository — optional

Your platform

With read access to your product's source code, Claude answers product questions from the code itself — how a feature actually works today, what limits apply, whether a change is live — in plain language, with the evidence available on request. Optional. Read-only: Claude never changes the product's codebase from the Work OS.

What it gives you

You askSkillWithout the connection
"How does the export limit actually work today?" · "Is the new pricing live?" · "Do we support SSO?"/code-qa — answers from the code, concise, no jargonClaude says it has no grounded code access and gives you the exact question to ask an engineer

How it works

Three parts. Permission comes first: everyone who will ask questions about the code needs read access to it, and only the person who administers those repositories can give it — the Work OS cannot grant it for them. Then the Work OS keeps a small shared registry of your repositories: what each one is for and which product areas it covers, in your own words. Finally, each person's computer holds a read-only copy of the code that Claude may read but never edit — that copy stays private and is never uploaded to the Work OS.

If your product lives in several repositories

Most do — the app your customers use in one, the services behind it in another, mobile apps in a third. Each repository is connected separately and described in one sentence; that sentence is what lets Claude send a question to the right code, and when a question spans several repositories Claude looks in each of them. You don't have to do them all at once: start with the one or two that would answer most of your questions, and add the rest whenever you need them.

Tip

If instead all your product's code sits in one large repository, that is the simplest case — connect it once, and Claude will ask which folders matter so it doesn't wander through the rest.

Before you start

Step 1 — Decide which repositories to connect (Work OS admin)

  1. List the repositories holding the code behind the product decisions you make: the app your customers use, the services behind it, the mobile apps. Ask an engineer to confirm the list — it takes them a minute.

  2. Leave out infrastructure, deployment and internal tooling repositories. They don't answer product questions, and they make every search noisier.

  3. Order what's left by how often you would ask about it. Connect the top one or two now; the rest can follow at any time.

Two or three repositories is a good place to start. Each one you add is another entry to keep fresh — and another place Claude has to look.

Troubleshooting

For Everyone

Your platform

What you might see, what it means, and what to do. Everything here is reported by Claude at the end of a response — you can always ask "what did auto-sync report?"

Claude notes "NO pull request opened … gh is not logged inaz lacks the azure-devops extension"

Your GitHubAzure sign-in on this computer is missing or expired. Redo Set up your computer, step 5. The note names the branch that was pushed — a Work OS admin can merge it once by hand from the repository page.

An everyday pull request stays "left OPEN — could not merge yet"

Either Allow auto-merge is off in the repository settings (Set up the repository, step 4) or a required check is still running. Auto-sync retries after every response.

A gated pull request merged without admin approval

One of: .github/CODEOWNERS still has the placeholder @[org]/os-admins (Customize the Work OS, step 2); the os-admins team lacks Write access; Require review from Code Owners is not ticked in the ruleset.

Either the reviewer policy is Optional instead of Required, or its path filter is outdated. The Work OS admin can ask Claude for the current line ("print the Azure path filter for the gated files") and the repository admin pastes it into the policy.

"/auto-sync status" says OFF for a teammate

The switch hasn't reached main yet, or the teammate's copy is behind. The Work OS admin checks that the setup pull request was merged (Customize the Work OS, step 3); the teammate asks Claude "pull the latest changes" and checks again.

"REBASE CONFLICT: sync/<you> does not rebase onto origin/main"

Someone changed the same file. Ask Claude: "resolve the rebase conflict on my branch, keeping both changes where possible" — it walks you through it. Auto-sync resumes at the next response.

Claude says the push to main was rejected

Expected for Work OS users — main is protected; auto-sync uses pull requests instead. If a Work OS admin sees it, check they are in the os-admins teamOS-Admins group.

How do we change which files are gated?

The Work OS admin edits the list in governance/write-policy.yaml (it is gated itself, so the change goes through "propose the gated changes"). .github/CODEOWNERS regenerates by itself.The repository admin pastes the new path filter into the branch policy — the pull request description contains the line.

Can I use the Work OS without auto-sync?

Yes, on your own — but your work stays on your computer until someone commits it by hand, and the team won't see it. Auto-sync is what makes it teamwork.

Can two people work at the same time?

Yes. Each person has their own branch; changes to different files never conflict. Changes to the same file are combined automatically when possible — see the rebase-conflict entry above for the rare case they aren't.
